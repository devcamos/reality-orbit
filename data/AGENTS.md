# Ontology and Curation Scope

## Purpose

This scope protects the Canonical Reality Ontology and its published curation data. It governs node names, paths, relationships, level limits, descriptions, and editorial approvals.

## Non-negotiables

- Reality is level 0; level 4 is the default maximum.
- Level 5 exists only for explicitly approved curated terminal concepts.
- Never force children merely to reach a target depth or child count.
- Never expand grandchildren unless the work item explicitly requests it.
- Never rename, merge, remove, reorder, or repurpose an existing canonical node without explicit governance approval.
- Preserve stable IDs, canonical paths, parent-child relationships, and node-specific teaching context.
- A concept may stop earlier when it is already meaningful and no further teaching relationship is approved.

## Change process

1. Read the linked ontology governance decision and backlog item.
2. State the proposed parent, one-level expansion, rationale, coverage, and boundary.
3. Check terminology, duplicate concepts, mutual exclusion, and long-term stability.
4. Update the curation record when a branch is approved.
5. Run ontology contract tests and review every affected path.

## Content rules

- Every node needs a stable ID, canonical path, label, definition, role, and complete node-specific Concept Anatomy.
- First principles must be concrete and node-specific.
- Do not use generic fallback language across dimensions or concepts.
- Visual styling may communicate a dimension, but it must not change canonical meaning.

## Safety boundary

User popularity, feedback volume, sponsorship, or payment must never directly determine whether an ontology claim is true or whether a canonical node changes.

## Field Notes → existing nodes

- Every Field Note must set `primaryNodeId` to an **existing** canonical ontology node.
- A teaching example (Probability under Model, Potential emergence under Framework, and similar) is not grounds to invent a new planet or leaf.
- Ontology expansion requires a separate governance ticket with an approved parent, one-level expansion, and curation update.
- Field Notes may deepen understanding of a node; they must not mutate the canonical graph.
